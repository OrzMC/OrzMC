# GitHub 迭代流程

> **状态：现行（建议） / 最后更新：2026-10-22**
>
> 本文为 OrzMC 父仓库及其子模块的统一迭代建议。各子模块自己的 `AGENTS.md`、`CONTRIBUTING.md` 和 CI 是具体门禁的事实源；本流程不替代它们。

## 目标与选择

采用**短生命周期分支 + Draft PR 尽早验证 + 子模块独立合并 + 父仓库显式锁定组合**的 PR 优先流程。各仓库沿用自己的目标分支和分支模型，不新增长期集成分支；例如 app 以 `main` 为目标，plugin 的开发分支约定仍按其子模块规则执行。单仓库的小改动独立推进；只有确实需要多个子模块共同实现一个产品行为时，才做跨仓协调。

这样能保留每个子模块独立发布和回滚的能力，同时让父仓库始终记录可复现的组合。GitHub Actions 负责平台矩阵与共享 CI；本机负责短反馈循环；人工评审和 UI 验收仍由维护者完成。日常迭代不需要额外引入 Project 看板或复杂 release train。

## 日常迭代

1. **确认目标与仓库。** 先读父仓库 `HANDOFF.md`，再读目标子模块自己的协作说明。确认改动属于父仓库内容还是某个子模块；代码和子项目配置在各自子模块仓库修改。
2. **从目标仓库规定的基线开短分支。** 命名用 `feat/<主题>`、`fix/<主题>`、`docs/<主题>` 或仓库既有约定。不要把 app、引擎和父仓库的工作混进一个代码分支。
3. **先跑本机快速检查，再按有意义的检查点推送。** 使用该仓库文档指定的 lint、单测或构建。把同一小目标的连续编辑攒成一轮推送，减少重复 CI；每次推送都应让 PR 留在可理解、可检查的状态。
4. **开 Draft PR 作为集成与反馈通道。** PR 描述写清问题、用户可见结果、实现范围、验证命令和剩余风险；跨仓任务互相链接 PR。Draft 阶段可以持续推送并收集 CI 结果，功能完成、门禁通过、人工验收条件具备后再标记 Ready for review。
5. **合并前检查对应仓库的全部必需门禁。** 不以本地成功替代 CI。不要用路径过滤或整份工作流跳过的方式让必需检查缺席；父仓库已发生过 release PR 因必需检查未上报而永久阻塞的情况。确需节省 CI 时，应保留同名必需状态并让不相关路径走成功的轻量检查。
6. **合并后清理分支并更新组合。** 子模块代码 PR 合并到该子模块默认分支后，父仓库才 bump 对应 gitlink。父仓库 PR 说明子模块仓库、合并 PR、目标 commit 和变更缘由；运行组合校验并核对 `git submodule status`、`git diff --submodule`。不要把未推送的子模块提交记录进父仓库。

## 跨子模块变更

先明确依赖方向和可独立验证的边界。分别在各子模块仓库开短分支和 Draft PR，PR 间互相引用；必要时消费者可临时指向依赖分支做集成验证，但发布组合只在依赖 PR 已合并、提交可从远端取得后更新。所有相关子模块 PR 通过后，在父仓库用一个产品级 PR 显式 bump 涉及的指针，并在描述中逐一列出。若实际可独立发布，拆成独立父仓库 bump，保持回滚粒度清晰。

父仓库一次纯指针提交通常只 bump 一个子模块；同一产品级变更确实需要多个子模块同步时，可在同一父仓库 PR 中一次性更新，并清楚列明各指针。不要顺手更新无关子模块到“最新”。

## app / SwiftUI 迭代

`swift/app` 的 PR CI 已分成快速平台分层检查，以及 macOS 与 iOS Simulator 两个构建目标。日常在本机用 `scripts/swift-check.sh` 的相应子命令先获得反馈；推送后由 GitHub CI 验证标准 runner 上的两平台构建。SwiftPM 依赖更新应作为明确的改动检查，避免无意中把解析漂移混入 UI PR。

涉及界面、导航、焦点、窗口或辅助功能时，Draft PR 可以先跑构建与测试，但完成视觉验收前保持 Draft。由维护者在目标桌面会话检查窗口尺寸、亮暗外观、键盘/焦点和真实操作路径；截图由维护者从桌面会话提供或操作采集。CI 不能代替 GUI 视觉验收。PR 中记录验收设备、场景和结论；未验收项列为明确的剩余工作。

保持 app 的单主启动器 `Window`、唯一 `AppModel`、平台分层、语义色和本地化约定。高风险架构或跨层改动可以在 Draft 阶段先做独立审查，避免到 Ready 阶段才发现方向问题。

## 合并、发布与仓库设置

- 只有在 PR 检查通过、审查/验收完成并由维护者决定后才合并。此流程不启用自动合并，也不把“CI 绿”视为发布授权。
- 发布使用子模块各自的发布流程；先按其指南跑 dry-run/打包验证，再由维护者触发正式发布。父仓库组合记录在发布前更新并核对。
- 仓库规则建议要求经 PR 合并、保护默认分支、要求当前 CI 必需检查通过；必需检查应使用稳定 job 名称，并确保所有 PR 类型（包括自动生成的 release PR）都会上报。父仓库已知有必需检查，其他仓库的规则设置须分别核对，不能假定一致。
- 不要求每个小 PR 都有 Issue 或看板卡片。若工作跨多个 PR、需要外部依赖或验收安排，使用一个 Issue 记录目标与完成条件，并在各 PR 互链即可。

## PR 完成清单

- [ ] PR 指向正确仓库与目标分支，范围单一且描述了结果。
- [ ] 本机快速检查完成，GitHub 上该仓库规定的必需 CI 全绿。
- [ ] 子模块改动遵守自身分支、版本、测试与发布约定。
- [ ] 跨仓依赖 PR 已互链；父仓库 gitlink 只指向可从远端取得的提交。
- [ ] UI 改动的人工桌面验收已完成；未完成时 PR 仍为 Draft 并记录剩余项。
- [ ] 父仓库改动运行组合校验，索引和交接信息按需更新。
- [ ] 合并与发布由维护者明确决定。
